# Участие в разработке

## Окружение

Нужен Python 3.10+.

```sh
python3 -m venv venv
./venv/bin/pip install --require-hashes -r requirements.lock
./venv/bin/pip install --no-deps -e .
./venv/bin/pip install --group dev
```

Зависимости ставятся из лока с проверкой хешей: сервер держит живой API-ключ,
поэтому подменённая зависимость здесь — это компрометация доступа, а не просто
сломанная сборка. `--group` требует pip 25.1 или новее.

## Тесты и линт

```sh
./venv/bin/python -m unittest discover -s tests -v
./venv/bin/ruff check .
```

Тесты не требуют сети: HTTP-клиент подменяется через `httpx.MockTransport`
(`tests/support.py`), а handshake по stdio проверяется на установленной команде
`ti-mcp`. Форматтер `ruff format` намеренно не включён в CI.

Версия `ruff` задана один раз, в группе `dev` в `pyproject.toml`, и CI ставит её
оттуда же — чтобы линтер на машине разработчика и в сборке не расходились.

## Зависимости

Версии задаются в `pyproject.toml`, `requirements.lock` из них генерируется.
После правки зависимостей лок нужно пересобрать, иначе CI это заметит:

```sh
uv pip compile pyproject.toml --universal --python-version 3.10 --generate-hashes -o requirements.lock
```

Флаги обязательны оба. `--universal` делает лок пригодным для всех платформ,
`--python-version` фиксирует нижнюю границу: без него uv резолвит под тот
интерпретатор, которым запущен, и результат зависит от машины.

## Контейнер

```sh
docker build -t ti-mcp .
```

Образ публикуется под `linux/amd64` и `linux/arm64`.

## Проверить сервер вручную

Сервер общается по stdio, поэтому его можно подёргать напрямую:

```sh
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  | TI_LOGIN=user@example.com TI_API_KEY=<key> ti-mcp
```

## Структура кода

| Модуль | Содержимое |
| --- | --- |
| `settings.py` | `Settings` — переменные окружения, читаются и проверяются один раз при запуске |
| `catalog.py` | справочник коллекций `COLLECTIONS` (датакласс `Collection`), устаревшие имена, `describe` |
| `params.py` | проверки отдельных аргументов, кеш `resultId` |
| `arguments.py` | модели аргументов тулов (pydantic): проверка вызова и `inputSchema` из одной модели |
| `client.py` | `TIClient` — HTTP-клиент: пул соединений, Basic-auth, троттлинг, ретраи, подсказки по статусам |
| `server.py` | тулы: описание, модель аргументов и обработчик каждого (`@tool`), состояние сервера (`AppState`), точка входа `cli` |

Глобального состояния нет: настройки, клиент с его троттлером и кеш `resultId`
создаются при старте сервера и живут, пока он работает. В тестах то же состояние
собирается из словаря переменных и подменённого транспорта — `tests/support.py`.

Тул добавляется в `server.py` функцией-обработчиком с декоратором `@tool(имя,
модель, описание)`; модель аргументов — класс в `arguments.py`. Из модели
строится `inputSchema`, и ею же проверяются аргументы до вызова обработчика, так
что схема и проверка не расходятся. Аргументу со своей проверкой из `params.py`
тип задаётся через `checked(...)`: проверка решает, что пропустить, и пишет
сообщение для модели, а в схеме остаётся простой JSON-тип. Порядок тулов в списке
— порядок их объявления.

Коллекция добавляется записью `Collection(...)` в `COLLECTIONS`: категория, лимит
записей, TTL, Admiralty-код, поддерживаемые фильтры, поля ответа. Что означает
каждое поле — в комментариях к `Collection`; `tests/test_catalog.py` проверяет,
что запись заполнена корректно.
Описания параметров тулов собираются из справочника, чтобы документация не
расходилась с кодом. Поля и лимиты сверяйте по гайдам TI API и по ответу живого
`ti_describe_collections` — на неизвестное поле в `q` бэкенд отвечает 400 с его
именем, так что ошибка в справочнике видна модели сразу.

## Документация

`README.md` (русский) и `README.en.md` — одно и то же содержимое на двух языках,
разделы совпадают один в один. Правку нужно вносить в оба файла. На PyPI уходит
русская версия: она указана в `readme` в `pyproject.toml`.

Оба файла публикуются и на GitHub, и на PyPI, поэтому:

- все ссылки абсолютные — PyPI не резолвит относительные пути;
- картинки только по абсолютному URL и только PNG или JPEG — SVG PyPI не покажет;
- без разметки, специфичной для GitHub (`> [!NOTE]`, `<picture>`) — санитайзер
  PyPI её вырежет.

Проверить, как страницу отрисует PyPI:

```sh
./venv/bin/pip install build twine
./venv/bin/python -m build && ./venv/bin/twine check dist/*
```

Логотип: `docs/logo.svg` — исходный знак с сайта, `docs/logo-banner.svg` — версия
для шапки, белый знак на фирменном тёмном, чтобы читаться и в светлой, и в тёмной
теме. `docs/logo.png` генерируется из баннера:

```sh
rsvg-convert -w 880 -h 264 docs/logo-banner.svg -o docs/logo.png
```

## Релиз

Версия задаётся в `src/ti_mcp/__init__.py` и оттуда попадает в метаданные
пакета, версию MCP-сервера и User-Agent. Публикация на PyPI и в GHCR происходит
по факту публикации GitHub Release; тег релиза (`vX.Y.Z`) должен совпадать с
версией пакета, иначе публикация остановится.
